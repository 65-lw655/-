# ADR 0002：记录级最后有效提交覆盖

- 状态：已采纳
- 日期：2026-08-09
- 决策范围：桌面离线同步与并发写入

## 背景

macOS 和 Windows 桌面端允许离线编辑。同一条业务记录可能在多台设备上被修改，客户端时间也可能不准确。用户已确认并发修改采用最后覆盖，不要求人工解决冲突。

如果以整个项目为覆盖单位，一条合同修改可能意外覆盖其他设备新增的回款、进度或照片。冲突粒度必须与可独立编辑的业务记录一致。

## 决策

1. 冲突粒度为单条业务记录，例如一笔合同、一条回款、一个里程碑或一项风险。
2. 最终顺序由服务器成功提交顺序决定，不使用客户端修改时间决定胜负。
3. 对同一记录，服务器最后接受的有效新增、修改或删除操作成为当前状态。
4. 操作必须先通过身份、项目权限和输入校验；被拒绝的操作不能参与最后覆盖。
5. 每个同步操作使用全局唯一 `operationId`。重复提交返回首次处理结果，不再次修改记录。
6. 客户端提交 `baseRevision` 用于识别和记录覆盖事件，但首期不因版本落后拒绝有效写入。
7. 删除保存为墓碑并参与相同的服务器排序，防止离线设备重新创建已删除记录。
8. 覆盖事件记录操作者、设备、服务器提交序号、前后版本和字段摘要，供审计与问题追踪使用。

## 示例

1. 设备 A 和设备 B 都从合同修订号 7 离线修改。
2. A 的有效操作先到达服务器，生成修订号 8。
3. B 的有效操作后到达服务器，生成修订号 9，并覆盖 A 对该合同记录的修改。
4. A 下次拉取时收到修订号 9；合同之外的回款、里程碑等独立记录不受影响。

## 结果

### 正面影响

- 规则简单，可在两台设备、长时间离线和重复提交场景中确定性推导结果。
- 不依赖不可靠的客户端时钟。
- 记录级覆盖减少无关业务数据被一并覆盖的范围。
- 审计信息可说明哪次提交覆盖了哪一版数据。

### 约束与代价

- 后提交的合法修改可能覆盖先提交内容，用户不会收到人工合并界面。
- 业务记录必须合理拆分；过大的记录仍会放大覆盖范围。
- 审计字段摘要不得包含密码、令牌、完整文件内容或其他敏感信息。
- 服务器必须保证提交序号单调递增，并将业务写入、操作幂等结果和审计记录作为一致处理单元。

## 未采用方案

### 字段级自动合并

不同字段之间可能存在业务约束，通用自动合并容易产生从未由任何用户提交过的组合状态。

### 人工冲突解决

会增加离线队列阻塞、界面复杂度和用户操作成本，不符合已确认的最后覆盖规则。

### 以客户端时间决定

设备时钟可能错误或被调整，无法作为可信的全局顺序。

## 复审触发条件

出现以下任一情况时重新评估字段级策略或人工合并：

- 审计数据显示关键记录发生不可接受的高频覆盖。
- 法务、财务或审批数据要求任何更新都不能静默覆盖。
- 单条记录持续扩大，无法通过合理拆分降低冲突范围。
