# ADR 0001：首期采用模块化单体

- 状态：已采纳
- 日期：2026-08-09
- 决策范围：首期服务端与工程结构

## 背景

系统首期服务 200 名用户、1000 个项目，文件每年增长约 200GB。客户端包括浏览器、macOS 和 Windows；桌面端还需要离线编辑、恢复网络后自动同步。

首期重点是尽快建立稳定的账号权限、项目业务、同步和文件链路。当前规模不要求通过微服务换取独立扩缩容，过早拆分还会增加接口协调、分布式事务、部署和排障成本。

## 决策

1. 服务端采用 TypeScript 模块化单体，通过清晰的模块边界组织账号权限、项目、合同回款、进度、造价、风险待办、文件、同步和审计能力。
2. Web 使用 React；macOS 与 Windows 使用 Tauri，并尽量共用 React 界面和领域规则。
3. 中央业务数据使用 PostgreSQL，文件内容使用国内云对象存储。桌面端使用本机 SQLite 保存离线业务数据和同步队列。
4. 后台任务与 API 共用同一代码库和领域模块，但作为独立进程部署，处理文件、清理和异步任务。
5. 首期不引入微服务、Kubernetes、消息队列或 Redis。只有在实际指标证明需要时再增加组件。
6. 模块之间通过显式服务接口交互，不允许直接依赖其他模块的内部实现。

## 结果

### 正面影响

- 单一代码库便于统一权限、事务、审计和同步规则。
- 开发、测试、部署和本地调试链路更短。
- API 与后台任务可以独立扩容，同时保持同一套业务规则。
- 将首期运维复杂度控制在当前团队和容量可承受范围内。

### 约束与代价

- 必须持续维护模块边界，避免形成无边界的大型应用。
- 单个发布包含多个业务模块，需要完善回归测试和渐进发布。
- 数据库仍是共享基础设施，重查询和后台任务必须受控，避免影响在线请求。

## 未采用方案

### 微服务

当前容量和团队协作规模不足以抵消服务发现、分布式追踪、跨服务一致性和多套部署流水线带来的成本。

### 仅浏览器 PWA

不能充分覆盖长时间离线、本地文件缓存、macOS 日历和提醒事项、Windows 凭证与安装包交付等桌面能力。

### 直接使用低代码或通用 BaaS

项目级权限、离线同步、文件生命周期和国内云部署约束需要明确的服务端控制面，通用平台会引入额外绑定和规则落差。

## 复审触发条件

出现以下任一情况时重新评估拆分服务或增加基础设施：

- 单一模块的吞吐、发布频率或故障隔离需求明显高于其他模块。
- 后台任务持续影响 API 延迟，且独立进程和数据库调优仍无法解决。
- 多团队需要独立发布并对模块承担明确的运行责任。
- 实测同步或通知负载需要专用消息基础设施。
