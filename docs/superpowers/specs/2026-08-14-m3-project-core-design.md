# M3 项目核心与成员管理闭环设计

## 1. 目标

M3 交付首个完整的在线项目管理纵切面：用户登录后可以按权限查看项目列表和详情，管理员可以创建项目，授权成员可以编辑项目，项目负责人和管理员可以完成成员新增、移除及角色调整，所有有效业务变更均生成全局提交序号和项目审计记录。

本阶段完成后：

- `USER` 只能查看自己参与的项目，`LEADER` 和 `ADMIN` 可以全局查看项目。
- `ADMIN` 可以创建项目并指定首位项目负责人。
- 项目 `OWNER`、`EDITOR` 和 `ADMIN` 可以编辑项目基础信息。
- 项目 `OWNER` 和 `ADMIN` 可以新增、移除成员及调整成员角色。
- Web 提供项目列表、详情、编辑和完整成员管理界面。
- 保存中、保存成功、校验失败、权限不足和网络失败均有明确状态。
- 每次成功的项目或成员变更都在同一数据库事务中写入业务数据和审计事件。

M3 不包含合同、收付款、风险、文件、导入导出、离线同步、桌面端业务界面，也不迁移现有本地项目数据。

## 2. 已确认前提

- 允许本项目进行数据库和 SQL 开发。
- 不读取、不转换、不迁移现有本地项目数据。
- 采用原生 `pg`、参数化 SQL 和版本化 SQL 迁移，不引入 ORM。
- M2 身份、会话和用户状态继续使用现有 `AuthStateStore` 文件仓储。
- M3 项目、项目成员、项目审计和全局提交序号存储在 PostgreSQL。
- 项目成员通过稳定的 M2 用户 ID 关联；本阶段不在 PostgreSQL 中复制用户账号。
- 并发保存采用后提交覆盖前提交，不因客户端版本落后拒绝保存。
- M3 使用虚构开发和测试数据，不接触真实业务数据或敏感凭证。

## 3. 成功标准

M3 只有同时满足以下条件才视为完成：

1. 项目列表、筛选、详情、创建、编辑、归档和恢复 API 按权限工作。
2. 成员列表、新增、移除、角色及成员资料调整 API 按权限工作。
3. Web 可以完成登录后进入项目列表、打开详情、编辑项目和管理成员的完整流程。
4. 普通用户、领导、管理员和三种项目成员角色的允许与拒绝路径均有自动化测试。
5. 最后一名 `OWNER` 不能被删除或降级，重复成员不能被添加。
6. 每次有效写入只生成一个新的全局提交序号，并生成对应审计事件。
7. 数据库迁移可以在空 PostgreSQL 数据库上重复、安全地执行到最新版本。
8. `npm run verify` 通过，且 PostgreSQL 集成测试在隔离测试数据库中通过。

## 4. 总体架构

### 4.1 存储边界

M2 和 M3 暂时采用双仓储：

- `AuthStateStore` 保存用户、账号状态、凭证、会话和安全审计。
- PostgreSQL 保存项目、项目成员、项目业务审计和全局提交序号。

项目成员表只保存 M2 用户 ID，不建立数据库用户外键。新增成员时，业务服务必须通过 `AuthStateStore` 验证目标用户存在、账号启用且凭证状态为 `READY`。已停用用户的成员关系不会自动删除，但该用户无法通过 M2 会话校验访问项目。

### 4.2 模块边界

- `packages/domain/src/projects/`：项目字段、状态、成员角色、输入校验和纯领域规则。
- `apps/api/src/modules/projects/`：项目及成员应用服务、仓储接口、PostgreSQL 实现和 HTTP 路由。
- `apps/api/src/modules/audit/`：项目业务审计类型及查询服务；M2 安全审计保持不变。
- `apps/api/src/database/`：连接池、事务边界、迁移执行器和迁移文件。
- `apps/web/src/features/projects/`：项目列表、详情、编辑、成员管理和业务审计时间线。

Fastify 路由只负责 Cookie 会话解析、JSON Schema 校验和 HTTP 映射。应用服务统一执行授权、用户状态验证、事务和业务规则。仓储只执行参数化 SQL，不包含权限判断。

### 4.3 事务与提交序号

每次有效写操作在单一 PostgreSQL 事务中按以下顺序执行：

1. 校验当前会话、账号、项目和成员权限。
2. 校验请求业务规则。
3. 从 PostgreSQL 全局序列取得新的 `commit_sequence`。
4. 更新业务记录，并递增项目 `revision`。
5. 写入一个对应的项目审计事件。
6. 提交事务。

校验失败、权限不足或写入失败时事务回滚，不产生业务可见的提交记录；PostgreSQL 序列允许因事务回滚出现空号，但已提交记录的序号始终唯一且递增。后提交的请求覆盖先提交结果；响应返回最新 `revision` 和 `commitSequence`。

## 5. 数据模型

### 5.1 `projects`

项目保存：

- `id`
- `name`
- `year`
- `type`
- `status`
- `phase`
- `lifecycle`：`ACTIVE | ARCHIVED`
- `filing_status`
- `planned_completion_date`
- `actual_completion_date`
- `created_at`、`created_by`
- `updated_at`、`updated_by`
- `revision`
- `commit_sequence`
- `archived_at`、`archived_by`

项目状态使用既有领域模型：中标待签、施工中、深化中、完工未验收、待验收、验收未结算、结算未回款、已结算待回款。归档和恢复使用独立操作，不允许普通编辑接口直接修改 `lifecycle`。

### 5.2 `project_members`

成员保存：

- `id`
- `project_id`
- `user_id`
- `member_role`：`OWNER | EDITOR | VIEWER`
- `job_title`
- `phone`
- `remark`
- `created_at`、`created_by`
- `updated_at`、`updated_by`

同一项目中的 `user_id` 唯一。项目始终至少保留一名 `OWNER`，删除或降级最后一名 `OWNER` 必须返回冲突错误。

### 5.3 `project_audit_events`

审计事件保存：

- `id`
- `project_id`
- `commit_sequence`
- `event_type`
- `actor_user_id`
- `target_type`
- `target_id`
- `change_summary`
- `occurred_at`

事件类型至少包含项目创建、项目修改、归档、恢复、成员新增、成员修改和成员移除。`change_summary` 只保存字段名及必要的安全前后值，不保存密码、会话、一次性码、Token 或请求头。

### 5.4 数据库基础对象

- `schema_migrations` 记录已应用迁移版本和执行时间。
- PostgreSQL 序列 `project_commit_sequence` 生成全局递增提交序号。
- 首个迁移只创建空结构、约束和必要索引。
- 开发虚构数据由独立种子命令创建，迁移文件不插入业务样例数据。

## 6. 授权规则

统一复用 M2 `AuthorizationService`，并按实时项目成员关系计算权限：

| 操作 | `USER` | `LEADER` | `ADMIN` |
| --- | --- | --- | --- |
| 项目列表与详情 | 需要成员关系 | 全局允许 | 全局允许 |
| 创建项目 | 拒绝 | 拒绝 | 允许 |
| 编辑项目 | `OWNER/EDITOR` | `OWNER/EDITOR` | 允许 |
| 归档与恢复 | `OWNER` | 成为 `OWNER` 时允许 | 允许 |
| 查看成员 | 需要项目读取权 | 全局允许 | 全局允许 |
| 新增、修改、移除成员 | `OWNER` | 成为 `OWNER` 时允许 | 允许 |
| 查看项目审计 | `OWNER` | 全局允许 | 全局允许 |

未登录返回 `401`。已经登录但无权执行已确认存在资源的操作返回 `403`。对于不应向调用者暴露项目是否存在的项目详情、成员和审计请求，统一返回 `404`。

## 7. API 契约

### 7.1 项目接口

| 方法与路径 | 作用 | 成功结果 |
| --- | --- | --- |
| `GET /api/v1/projects` | 分页查询可见项目 | `200` |
| `POST /api/v1/projects` | 创建项目并指定首位负责人 | `201` |
| `GET /api/v1/projects/:projectId` | 查询项目详情及当前用户可执行操作 | `200` |
| `PATCH /api/v1/projects/:projectId` | 修改项目基础信息 | `200` |
| `POST /api/v1/projects/:projectId/archive` | 归档项目 | `200` |
| `POST /api/v1/projects/:projectId/restore` | 恢复项目 | `200` |
| `GET /api/v1/projects/:projectId/audit-events` | 分页查询业务审计时间线 | `200` |

列表支持 `query`、`year`、`status`、`lifecycle`、`page` 和 `pageSize`。默认按最近更新时间降序。`pageSize` 设置固定上限，所有文本、枚举、日期和分页字段由 JSON Schema 校验并拒绝额外字段。

项目详情只返回项目信息和当前用户的权限标志；成员列表由独立成员接口返回，避免重复维护两套响应。

### 7.2 成员接口

| 方法与路径 | 作用 | 成功结果 |
| --- | --- | --- |
| `GET /api/v1/projects/:projectId/members` | 查询成员列表 | `200` |
| `GET /api/v1/projects/:projectId/member-candidates` | 搜索可添加用户 | `200` |
| `POST /api/v1/projects/:projectId/members` | 新增成员并指定角色 | `201` |
| `PATCH /api/v1/projects/:projectId/members/:memberId` | 调整角色和成员资料 | `200` |
| `DELETE /api/v1/projects/:projectId/members/:memberId` | 移除成员 | `204` |

成员候选搜索仅允许项目 `OWNER` 和 `ADMIN` 调用，`query` 至少两个字符，最多返回 20 个启用且凭证就绪的非项目成员。响应只包含用户 ID、登录名和显示名称。

新增成员前再次从 `AuthStateStore` 验证目标用户状态。重复成员返回 `409`。最后一名 `OWNER` 的删除或降级返回 `409`。本阶段不提供批量成员操作。

### 7.3 错误响应

错误响应沿用统一结构和稳定错误码：

- `400`：请求结构或字段校验失败。
- `401`：会话缺失、失效或账号不可用。
- `403`：调用者已登录但无操作权限。
- `404`：资源不存在，或需要隐藏资源存在性。
- `409`：重复成员、最后负责人保护或当前状态冲突。
- `500`：未预期服务端错误，不返回 SQL、凭证或内部堆栈。

## 8. Web 交互

### 8.1 项目列表

登录成功后进入项目列表。页面包含：

- 项目名称关键字、年度、状态和生命周期筛选。
- 项目名称、年度、类型、状态、阶段、负责人、更新时间和生命周期。
- 加载、空列表、筛选无结果、权限不足和网络失败状态。
- `ADMIN` 可见“新建项目”入口，其他角色不显示该入口。

筛选状态保存在页面 URL 查询参数中，刷新后可恢复；不保存凭证或敏感数据。

### 8.2 项目详情与编辑

项目详情展示基础信息、当前成员、审计入口和当前用户允许的操作。只有有权用户看到编辑、归档、恢复和成员管理按钮。

编辑使用表单完成，字段校验与服务端规则一致。保存期间禁用重复提交；成功后使用服务端返回的新数据刷新详情并显示成功提示；校验失败保留用户输入；`401` 返回登录界面；`403/404` 显示明确不可操作状态；网络失败允许用户重试。

后提交覆盖先提交时，页面以服务端成功响应为准，不弹出版本冲突对话框。

### 8.3 成员管理

成员管理区域提供：

- 成员列表：显示名称、登录名、项目角色、职位、电话、备注和账号状态。
- 新增成员：搜索用户、选择角色、填写可选成员资料并确认添加。
- 编辑成员：调整 `OWNER/EDITOR/VIEWER` 及成员资料。
- 移除成员：显示确认对话框后执行。
- 最后一名 `OWNER`：角色降级和移除操作禁用，服务端仍执行最终保护。

只有 `OWNER` 和 `ADMIN` 显示管理操作。`EDITOR`、`VIEWER` 和只读 `LEADER` 只能查看成员列表。每次成功操作后刷新成员列表、项目详情权限和审计时间线。

### 8.4 审计时间线

有权限的用户可以查看按提交序号倒序排列的业务审计事件，展示操作类型、操作人、发生时间和安全变更摘要。界面不提供修改或删除审计记录的操作。

## 9. 数据库运行方式

- 本机开发使用项目内 Docker Compose 启动独立 PostgreSQL 服务和独立数据卷。
- 数据库地址、用户名和密码通过环境变量提供，不硬编码、不提交真实值。
- 仓库只提交不含凭证的 `.env.example`。
- API 启动前执行显式迁移命令；生产启动不隐式修改数据库结构。
- 自动化测试使用独立测试数据库，测试结束后只清理测试创建的数据。
- CI 使用临时 PostgreSQL 服务执行迁移和集成测试。

### 10.4 Web 测试

最终使用虚构账号和项目数据完成桌面与移动宽度下的浏览器流程验证。

## 11. 实施边界

为保持 M3 收敛，本阶段明确不做：

- 把 M2 用户、会话或安全审计迁移到 PostgreSQL。
- 迁移旧桌面项目数据或旧项目字段。
- 项目批量编辑、批量成员导入或组织架构同步。
- 乐观锁冲突提示、历史版本恢复或审计导出。
- 合同、财务、风险、文件和离线同步能力。

以上能力进入后续里程碑，不作为 M3 完成条件。
